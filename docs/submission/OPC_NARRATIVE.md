## 一句话定位

**学航·转衔：面向转专业学生的 AI 学业路径重构 Agent。**
把学生转专业之后散落一地的课程问题，重构成一条**可执行、可解释、可确认**的学业路径。

其中：
- **学航** = 学业导航；
- **转衔** = 转专业衔接。

---

## 二、用户是谁

| 角色 | 他现在的处境 |
|---|---|
| **转专业学生（主要用户）** | 刚换到新专业，手里只有一份成绩单、一份新的培养方案、一个还没排完的本学期课表 |
| 辅导员 / 教务老师 | 被学生反复问"我还差哪些课""我这学期该选什么"，但每次都要重新对着条款翻一遍 |
| 学院负责人 / 评委 | 关心结论有没有依据、责任由谁承担、系统边界在哪儿 |

主要用户是**刚完成转专业、正在为接下来几个学期发愁的本科生**。

---

## 三、核心痛点

转专业以后，学生面对的不是"选哪门课"这么简单。他真正要回答的是一串连在一起的问题：

1. 我已经修过什么？
2. 目标专业还缺什么？
3. 哪些课程需要补修？
4. 本学期真实有哪些教学班可以上？
5. 当前课表冲不冲突？
6. 哪些问题必须人工确认？
7. 未来几个学期怎样把培养方案重新接起来？

现实里这七件事被拆散在四个不同的地方：成绩单在教务系统里，培养方案是一份文档，教学班在开课查询页面，课表在另一个页面。学生只能靠截图、手抄和记忆把它们拼起来。

### 这些问题有真实调研数据支撑

项目初期做过一次面向在校本科生的问卷调研（在线发放，回收 32 份，有效样本 24 份，有效率 75.0%，回收时间 2026 年 9 月 27 日）。结果与上述痛点吻合：

| 调研结果 | 数值 |
|---|---|
| 有转专业经历 | 91.7%（22 人） |
| 遇到"补修课程与现有课程时间冲突" | 75.0% |
| 认为"课程时间冲突"影响最大 | 70.8% |
| 遇到"想补的课程本学期没有开设" | 62.5% |
| 遇到"很难规划未来几个学期的补修顺序" | 58.3% |
| 表示"没遇到明显问题" | 仅 8.3%（2 人） |
| 知晓"如何处理补修课程与现有课表的冲突" | 仅 29.2% |
| 目前使用过 AI 工具 | 仅 16.7% |
| 最需要的功能：规划未来几个学期的补修路径 | 79.2% |
| 愿意使用能生成可执行方案的工具 | 70.8%，无人不愿意 |

> ⚠️ 这是小样本调研（有效 24 份）。结论用于确认需求方向与功能优先级，
> **不等同于**市场验证完成，也不作为市场规模或需求覆盖率的推断依据。
> 完整统计见 `docs/submission/support/01_用户需求调研与问卷分析.pdf`。

一个典型的真实状态是：**大部分问题都没有确定答案，而学生无法区分"已经确定"和"还不确定"。**

## 四、为什么现有的教务系统和选课工具解决不了

这一节只讲职责错位，不评价任何工具做得好不好。

| 现有工具 | 它擅长什么 | 它为什么回答不了转专业学生的问题 |
|---|---|---|
| 教务系统 | 把课程和教学班**列出来** | 它展示供给，不判断"你缺什么"。它不知道你转过专业，也不知道你的旧课能不能顶新课 |
| 通用选课助手 | 按时间、教师、给分偏好**帮你挑课** | 它假设你已经知道要选哪些课。转专业学生恰恰不知道，他要选的是"补什么" |
| 通用课程问答机器人 | 用自然语言**解释和回答** | 它可以说得头头是道，但说不出"这条结论的依据是哪一条培养要求"，也不能承担认定责任 |
| 学生自己手动对 | 灵活、零门槛 | 慢、容易漏、每学期都要重来一次，而且过程无法交接给别人复核 |

核心差距是一句话：

> 现有工具解决的是**"这学期选哪几门课"**，转专业学生需要解决的是**"接下来几个学期，我的培养方案怎么重新接上"**。

路径重构是一个独立的闭环，不是选课功能的一个子集。

## 五、产品闭环

系统把七件事收成一条链路：

```text
成绩单
  ↓  识别已修课程
培养方案要求
  ↓  逐条评估：已满足 / 待人工确认
补修需求
  ↓  对照本学期真实教学班
当前课表 + 个人偏好
  ↓  冲突检测与替代教学班建议
按归属分区的待确认事项
  ↓  你明确确认后才生效
本学期可执行课表
  ↓  按培养方案补足选修学分缺口
未来学期课程级路径
```

这条链路上，页面最终收敛成五段：

```text
1. 补修缺口分析
2. 本学期专业选修建议
3. 本学期推荐课表
4. 未来学期修读路径
5. 详细依据（默认折叠）
```

三个关键设计选择：

1. **每一段都给出依据**，不只给结论。学生能看到"为什么这条算已满足"，也能看到"为什么这条还不敢下结论"。
2. **系统只建议，不替你决定。** 换班建议必须由学生本人点"采用调整"才生效；选修必须由学生本人点"加入本学期方案"。
3. **不确定的地方如实说出来**，而不是用一个看起来完整的方案盖过去。

### 两处本轮新增的交互

**规划层确认（补修缺口分析内）**

学生可以对"待人工确认"的条目做一次**规划层确认**，系统据此重新计算本次方案，把这些项在**本次规划**里按已满足处理。
界面逐字写明：

> **基于你的确认**、**仅用于本次规划**、**不是学校官方认定结果**

每条确认都能**撤销**。用户确认**不会**改写 23 项 / 12 项 / 11 项那份有来源依据的基线事实。

**选修加入 / 撤销（本学期专业选修建议内）**

系统从当前学期真实教学班中筛出候选，**只有服务端确认无冲突（CLEAR）的教学班可以加入**：

- 唯一 CLEAR：可直接作为建议教学班加入，仍需学生显式点击；
- 多个 CLEAR：必须由学生自己选教学班，系统不会自动挑一个；
- 只有未知或冲突：不给加入按钮，并说明原因；
- 加入后标注为**规划草稿**，可随时撤销。

### 一条来自真实使用的经验

> 最初的界面把所有待确认事项平铺出来，真实数据下会变成 11 张卡片、一门课最多 60 个候选堆在一页，
> 学生根本读不完。后来把换班按课程分组、默认只显示 3 个候选，再把待确认事项收口进各区块。
> **把不确定性如实说出来，和把不确定性说清楚，是两件不同的事。**

### 一个容易被忽略的细节

真实数据里，**数据库系统原理**与**数据库系统实验**一直在专业选修池里、也有真实教学班，
但旧界面只显示前 3 个选修候选，把它们藏在了视野之外。问题不在数据，而在界面截断。
最终界面不再截断候选，学生能查到它们、看到真实教学班，并自己决定要不要加入。

## 六、技术架构

四层，自上而下：

```text
前端（Vue 3 单页应用）
    输入区：成绩单、当前课表、意向课程、偏好
    展示区：补修缺口分析、本学期专业选修建议、本学期推荐课表、未来学期修读路径、详细依据
        ↓  HTTP
后端（FastAPI）
        ↓
编排层：固定工具编排
        ├── Curriculum    培养方案差异与补修判定
        ├── Course Data   本学期教学班供给
        └── Planner       受限确定性检查与替代教学班候选
        ↓
公共结果：建议课表 / 变更记录 / 风险 / 待人工确认事项
```

架构上的两个要点：

- **编排层只做编排**，按固定顺序调用三个模块，自己不判断缺什么课、不检测冲突、不选班，也不改写结果；
- **跨模块只通过公共契约交互**（`schemas/` 与 `docs/interfaces/`），模块之间不依赖彼此的内部实现。

### 技术性质（必须如实说明）

**当前是规则驱动 + 结构化数据 + 确定性规划。**

- 是**固定工具编排**，不是自主决策 Agent，也不是多个 Agent 协商；
- 规划部分是**受限的确定性检查与候选评估**，不是全局最优；
- **AI 增强模块尚未接入**：当前没有大模型推理、没有检索增强、没有知识图谱推理，偏好来自结构化表单而不是自然语言。

产品方向上有 AI 的位置：未来由模型辅助理解输入、检索证据、生成解释。但这属于**后续增强**，不在当前执行链路上。

## 七、创新点

按"评委能当场验证"的顺序排列。

### 1. 把"转专业路径重构"当成一个独立问题来建模

不是把选课功能做得更聪明，而是承认转专业学生面对的是一个**跨学期的路径重接**问题：历史已修事实、目标培养要求、本学期供给、时间约束、认定边界，这五类信息必须放在同一个模型里才能回答。

### 2. 课程与教学班分成两层

课程本身跨学期相对稳定，教学班每学期全变。系统把两者分开建模，因此"同一门课的多个教学班"天然可查。这正是"这个班时间冲突，就换同课的另一个班"能够成立的基础。

### 3. 结论带证据等级，不确定性是一等公民

每一条培养要求都带明确状态：**已满足 / 待人工确认**。系统不会把"看起来像"写成"已经认定"。

时间冲突的判定也是三态而不是两态：

```text
已确认冲突  >  信息未知  >  在已知信息范围内未发现冲突
```

排课信息缺失时，结论只能表述为"与当前课表中已知的时间段未发现冲突"，整体仍然是未知。**信息未知不等于没有冲突。**

### 4. 建议与生效分离，人留在回路里

换班建议是结构化候选，生成建议不会改动课表。只有学生本人明确确认某一条，系统才应用它。

### 5. 未来规划诚实降级

未来学期只做**课程级**规划：哪几门课、几个学分、必修还是选修、建议放在哪个学期。
未来学期**不出现**教学班、教师、上课时间、教室、校区、容量——因为教务系统只提供本学期真实开课信息，编造这些字段就是伪造数据。

## 八、Human-in-the-loop（人机边界）

系统把"人"放在三个位置上。

### 第一处：认定权留给人

课程是否等价、学分差额怎么算、学院有没有特殊政策、培养方案条款有歧义——这些一律标记为**待人工确认**，系统不下正式结论，只把依据显示出来。

> 权威始终在学校。系统的价值是让人做决定时手里有完整的证据清单。

### 第二处：执行权留给人

- 系统**不会**自动换班、自动选课、自动注册；
- 换班建议生成后课表保持不变；
- 学生点"采用调整"之后，系统才重新计算并返回新课表；
- 手填的当前课表默认不被采用，必须由学生本人勾选确认"这是我自己填的"，确认之后如果课表又被改动，确认自动作废。

### 第三处：诚实失败

前置条件不满足时，系统明确拒绝并说明原因，**不会**退回演示数据顶替，也不会假装成功。

### 第四处：风险透明

数据范围、待确认事项、无法执行的部分，都在页面上如实列出，不折叠、不隐藏、不写成结论。

## 九、当前限制

这一节必须原样保留，不允许在润色时删除或弱化。

### 已实现（当前产品基线可运行的范围）

- 成绩单 PDF 导入，识别已修课程（不猜课程号）；
- 培养要求**逐条**评估：已满足 / 待人工确认；
- 本学期**真实教学班级别**规划，数据为**南校园 + 深圳校区**（4069 条教学班，case-scoped）；
- 冲突检测（三态，`信息未知` 不等于无冲突）；
- 换班候选建议（按课程分组，多候选聚合展示）；
- **用户明确确认之后才应用**换班；
- 未来学期**课程级**路径规划；
- 专业选修学分规划，以及本学期专业选修建议；
- **规划层确认**：对待人工确认项做"本次规划按已满足处理"的确认，可撤销，且明确不是学校官方认定；
- **本学期专业选修的加入与撤销**：只有服务端确认无冲突的教学班可加入，多候选必须用户自己选；
- 学分负荷控制（当前学期上限 30，未来学期软目标 26、硬上限 35）；
- 页面五段结构，待确认事项收口在各区块内部，技术细节折叠在"详细依据"。

### 数据范围

- 当前数据是**南校园 + 深圳校区**两个校区的 scoped 数据，**不是**完整学期数据，**不是**全校完整课程数据；
- 页面会明确标注这一点。

### 未来学期的粒度

- 未来学期只做**培养方案课程级**路径规划；
- **不预测**未来教师、时间、教学班、容量。

### 仍未具备的能力

- 未接入大模型推理、检索增强、知识图谱推理；
- 未使用全局优化求解；
- 不做自动选课、不做自动课程等价认定、不做自动课程替换；
- 没有自然语言偏好解析，偏好来自结构化表单；
- 先修关系的真实来源目前没有证据；
- **当前 accepted Course Data 快照未保留教师字段，因此教师信息暂未同步**，页面用中性文案说明，系统不编造教师；
- **规划层确认不是学校官方认定**：它只作用于本次规划，可撤销，也不改写有来源依据的基线事实；
- **数据库系统原理与数据库系统实验在本学期并未被学生选中**：它们是可查询的选修候选，只有用户明确加入后才计入当前负荷。

### 学分负荷

系统对每学期建议的学分总量有控制：

- 当前学期默认学分上限 **30**；
- 未来学期软目标 **26 学分**，硬上限 **35 学分**；
- 负荷标签：≤26 正常 / 26–30 较满 / 30–35 很满，任何学期都不得超过 35；
- 用户自己设置的学分上限优先，用户值超过对应硬上限时按硬上限收口；
- 注意：当前学期上限和未来学期上限是**两个不同的值**（30 / 35），不要混用。

之所以要有这条约束，是因为没有它的时候真实规划会产出单学期 50 学分以上的不可执行方案。宁可把课程推迟到后面的学期，也不塞进一个学生上不完的学期。

### 两个必须特别小心的数字口径

材料里会出现两个 **23**，它们完全不是一回事。

**第一个 23：培养要求评估条数**

> **23 项历史培养要求评估**，其中 **12 项已确认满足**，**11 项需要人工确认**（0 项已确认需补修）。

**不能说成"需要补修 23 门课"。**
这 23 项是逐条评估的结果，其中 11 项目前还不能下结论，需要人工确认，它们不等于"确认要补的课"。

**第二个 23：学分**

> 目标专业选修组的最低毕业要求是 **23 学分**。

这是**学分**，不是课程门数，也不是补修任务数。
本次真实数据里，选修组共有 37 门候选课程，学生只需在其中补足 23 学分即可，**不需要把 37 门都修完**。

> 一句话区分：**23 项是"评估了多少条要求"，23 学分是"选修要修满多少分"。**

## 十、竞赛叙事（商用语言版）

给评委讲的时候，用这个顺序。

### 第 1 句：我们盯住的是谁

"我们服务的是刚转完专业的学生。他手里有一份成绩单、一份新专业的培养方案、一个还没排完的课表。"

### 第 2 句：他的问题不是选课

"他真正要回答的是：我已经修过什么、目标专业还缺什么、哪些必须补、本学期真实有哪些班能上、课表冲不冲突、哪些要问老师、后面几个学期怎么接。这七件事现在散在四个不同的地方。"

### 第 3 句：现有工具为什么接不上

"教务系统负责把课列出来，选课助手负责帮你挑课。它们都假设你已经知道要选什么。转专业学生不知道，他要先知道缺什么。"

### 第 4 句：我们做了什么

"我们把这条链路重构成一条可执行、可解释、可确认的学业路径：从成绩单和培养方案出发，先做历史培养要求的逐条评估，再对照本学期的真实教学班做冲突检测和替代建议，最后由学生本人确认。"

### 第 5 句：我们的边界在哪里，为什么这是优点

"我们只做我们能证明的部分：本学期精确到真实教学班，未来学期只做课程级规划。认定类的问题一律交回给人。信息不足时我们说的是'还不知道'，不是'没问题'。"

### 第 6 句：为什么这是一个可以长大的产品

"这套结构不依赖某一所学校：换培养方案、换校区、换认定规则，改动集中在数据适配层。越往后积累的教学要求评估结果和确认记录，就越有价值。"

## 十一、这套叙事里最容易讲错的三件事

| 容易讲错 | 正确说法 |
|---|---|
| "系统帮学生自动排好了最优课表" | 系统给出**建议方案**与待确认调整，学生本人确认后才生效 |
| "23 门课要补" | **23 项历史培养要求评估**，12 项已确认满足，11 项待人工确认 |
| "我们用 AI 推理出了缺哪些课" | 当前是规则驱动 + 结构化数据 + 确定性规划，AI 增强待接入 |

## 十二、给润色同学的提示

- 这份叙事是**事实母本**，可以做的是改语气、调节奏、换比喻；
- ⛔ 不能做的是改数字口径、扩大数据范围、把"待确认"写成"已确认"、把"建议"写成"已执行"；
- 每一处需要等 UI 定稿才能写死的地方，在相关文件里都留了 `[待 UI 定稿]` 之类的占位。
