## 这一轮的交互与页面结构变化（截图对应的版本特征）

最终主流程是五段：

```text
1. 补修缺口分析
2. 本学期专业选修建议
3. 本学期推荐课表
4. 未来学期修读路径
5. 详细依据
```

- **不再有独立的大块"待你确认的调整"模块**；待确认事项收口到各区块内部。
- 补修缺口分析里新增**规划层确认**交互：勾选 → 确认 → 本次规划按已满足处理 → 可撤销。
- 本学期专业选修建议变成**可操作区**：加入本学期方案 / 已加入 / 撤销。
- 课表区新增**来源图例**，区分当前已选、规划新增/建议、你加入方案的选修。

- **取景**：页面顶部品牌区与定位
- **用途**：PPT 或评委快速理解产品定位

- **不能证明**：不证明任何规划结论

### 01_上传成绩单.png
- **取景**：「第一步：上传成绩单」区块
- **用途**：证明输入起点是学生本人成绩单
- **配文**：「系统只取课程名称、学分、成绩与学期；姓名、学号、绩点不读取、不展示。」
- **不能证明**：不证明成绩单内容已被学校核验

### 02_补修缺口分析.png
- **取景**：「补修缺口分析」整块（含筛选页签、规划确认入口、任务表格）
- **用途**：核心画面。证明培养要求被逐条评估，且"待人工确认"没有被写成"需要补修"
- **画面内容**：页签计数 **全部任务 (23) / 待人工确认 (11) / 已满足 (12)**；逐条任务的判定状态与认定依据；
  **没有出现「需要补修」页签**（因为本次数据里该项为 0，计数为 0 的页签不渲染）
- **配文**：「23 项历史培养要求评估：**12 项已满足、11 项待人工确认**。待人工确认不等于需要补修——
  课程是否等价、学分怎么算属于学校正式规则，系统只列依据，不下结论。」
- **不能证明**：不证明这些判定对任何其他学生成立

### 03_待人工确认页签与确认入口.png
- **取景**：规划确认面板（披露文案 + 三个动作按钮）
- **用途**：证明系统允许用户对未确认项做**规划层确认**，并把边界写在按钮上方
- **画面内容**：披露句「勾选后可标记为**本次规划按已满足处理**：基于你的确认、仅用于本次规划；
  **不是学校官方认定结果**」；按钮「全选可确认项 / 清空选择 / 确认所选并重新规划」；提交按钮上是**精确条数**
- **配文**：「用户可以勾选待人工确认项，标记为本次规划按已满足处理。系统同时写明：这是**基于你的确认**、
  **仅用于本次规划**、**不是学校官方认定结果**。」
- **不能证明**：⛔ 不证明学校已认定课程等价，⛔ 不证明补修认定被批准

### 04_确认后状态与撤销.png
- **取景**：确认结果区与撤销入口
- **用途**：本套材料里最重要的 Human-in-the-loop 截图
- **画面内容**：标题「本次规划已确认满足（N 项）—— 基于你的确认、仅用于本次规划；不是学校官方认定结果」；
  逐条列出已确认课程号 + 「基于你的确认」标记 + 「撤销确认」按钮
- **配文**：「确认之后，这些项在**本次规划**里按已满足处理，下游方案随之重新计算；每一条都可以**撤销确认**。
  注意标记写的是'基于你的确认'，不是'学校已认定'。」
- **⚠️ 采集说明**：本次演示为了展示交互，确认了该轮**全部可确认项（11 项）**。数字本身不是结论，
  只表示"用户把可确认项全确认了"。⛔ 不要用这张图声称"11 项已被认定为满足"。
- **不能证明**：⛔ 不证明学校承认这些课程等价，⛔ 不证明 source-backed 基线被改写
