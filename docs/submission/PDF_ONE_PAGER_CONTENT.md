## 三、用户痛点（80–110 字）

转专业以后，学生要连续回答七个问题：我已经修过什么、目标专业还缺什么、哪些课需要补、本学期真实有哪些教学班、课表冲不冲突、哪些必须问老师、后面几个学期怎么接。

这七件事散在成绩单、培养方案、开课页面和课表里。学生只能靠截图和记忆拼，最容易出错的恰恰是最要紧的部分。

### 调研数据支持（真实统计，可直接引用）

问卷调研：回收 32 份，有效样本 24 份。受访学生中 **75%** 遇到补修课程与现有课程时间冲突，**70.8%** 认为这是影响最大的问题；**仅 8.3%** 表示没遇到明显问题；**仅 29.2%** 知道该怎么处理课表冲突；**仅 16.7%** 用过 AI 工具；最需要的功能是"规划未来几个学期的补修路径"（**79.2%**）。

> 小样本（有效 24 份），仅用于确认需求方向。完整统计见支撑材料 `01_用户需求调研与问卷分析.pdf`。

## 四、四步流程（每步一句话）

| 步骤 | 一句话 |
|---|---|
| **第一步 上传成绩单** | 系统识别你已经修过哪些课程，覆盖几个学期 |
| **第二步 填写当前课表** | 搜索课程加入，或手工录入并本人确认 |
| **第三步 生成方案** | 系统逐条评估培养要求，结合本学期真实教学班给出推荐课表 |
| **第四步 确认与调整** | 未确认项可提交规划确认、选修可加入方案、换班可点采用调整；全部可撤销 |

结果按五段呈现：**补修缺口分析 → 本学期专业选修建议 → 本学期推荐课表 → 未来学期修读路径 → 详细依据**。

## 五、主要功能（九条，每条不超过 22 字）

1. **成绩单导入**：识别已修课程，覆盖几个学期
2. **培养要求逐条评估**：已满足还是待确认，一条条列清楚
3. **规划层确认**：勾选后可标记为本次规划按已满足处理，可撤销
4. **本学期真实教学班规划**：精确到具体教学班
5. **课表冲突检测**：冲突、未知、未发现冲突，三种状态分开讲
6. **换班候选建议**：当前班到候选班，附调整原因
7. **本学期专业选修建议**：还差学分时给出可加入的专选，支持撤销
8. **未来学期课程路径**：哪几门课、几个学分、放哪个学期
9. **选修学分进度**：要求、已完成、已选、还差多少，一笔一笔算清

## 六、产品差异化（三条）

**一、它回答的不是"选哪门课"，而是"路径怎么接"。**
现有工具都在解决本学期选课，我们解决的是跨学期的路径重构。

**二、它把"不确定"当成正式结果。**
每一条培养要求都带状态，是已满足还是待人工确认，页面直接写出来。信息不足时说"还不知道"，不说"没问题"。

**三、它只建议，不替学生决定。**
换班建议生成后课表不动，学生本人确认后才生效。课程等价这类问题一律交回学校认定。
**学生可以做"仅用于本次规划"的确认**，界面同时写明这不是学校官方认定结果，且可以撤销。

## 七、架构条（一行式，用于页面底部）

```text
成绩单 → 培养要求评估 → 补修需求 → 本学期真实教学班 → 冲突检测与换班候选
      → 学生确认 → 本学期课表 → 未来学期课程路径
```

技术性质一行注明：

> 规则驱动 + 结构化数据 + 确定性规划；固定工具编排，AI 增强模块待接入。

## 九、人工确认 / 可信设计（三条）

- **认定留给人**：课程等价、学分差额、学院政策、条款歧义，系统不下正式结论，只列依据；
- **确认也是规划层的**：学生的确认标记为「基于你的确认 / 仅用于本次规划 / 不是学校官方认定结果」，并且可撤销；
- **执行留给人**：不自动选课、不自动换班；选修必须学生点「加入本学期方案」；手工填写的课表必须本人确认，改动后确认自动作废；
- **风险透明**：数据范围、待确认事项、未执行的偏好，全部如实展示，不隐藏、不改写。

## 十一、当前限制（六条，建议保留在宣传页底部小字）

1. 教学班数据范围为**南校园 + 深圳校区**，共 4069 条，不是全校、不是完整学期数据；
2. 未来学期只做**课程级**规划，不预测教师、时间、教学班、容量；
3. 系统**不执行**选课与注册，输出为建议方案；新增的选修加入只是**规划草稿**；
4. 大模型、检索增强、自然语言偏好解析**尚未接入**；
5. **当前 accepted Course Data 快照未保留教师字段，因此教师信息暂未同步**；
6. **规划层确认不是学校官方认定**，仅用于本次规划且可撤销；数据库系统原理（CSE335）与数据库系统实验（CSE337）
   是**可查询的选修候选**，本学期并未被学生选中。
