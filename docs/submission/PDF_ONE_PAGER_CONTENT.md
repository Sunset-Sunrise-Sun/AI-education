## 三、用户痛点（80–110 字）

转专业以后，学生要连续回答七个问题：我已经修过什么、目标专业还缺什么、哪些课需要补、本学期真实有哪些教学班、课表冲不冲突、哪些必须问老师、后面几个学期怎么接。

这七件事散在成绩单、培养方案、开课页面和课表里。学生只能靠截图和记忆拼，最容易出错的恰恰是最要紧的部分。

---

## 四、四步流程（每步一句话）

| 步骤 | 一句话 |
|---|---|
| **第一步 上传成绩单** | 系统识别你已经修过哪些课程，覆盖几个学期 |
| **第二步 填写当前课表** | 搜索课程加入，或手工录入并本人确认 |
| **第三步 生成方案** | 系统逐条评估培养要求，结合本学期真实教学班给出推荐课表 |
| **第四步 确认调整** | 换班建议由你本人点选确认后才生效 |

---

## 五、主要功能（六条，每条不超过 22 字）

1. **培养要求逐条评估**：已满足还是待确认，一条条列清楚
2. **本学期真实教学班规划**：精确到具体教学班
3. **课表冲突检测**：冲突、未知、未发现冲突，三种状态分开讲
4. **替代教学班建议**：当前班到候选班，附调整原因
5. **未来学期课程路径**：哪几门课、几个学分、放哪个学期
6. **选修学分进度**：要求、已完成、已选、还差多少，一笔一笔算清

---

## 六、产品差异化（三条）

**一、它回答的不是"选哪门课"，而是"路径怎么接"。**
现有工具都在解决本学期选课，我们解决的是跨学期的路径重构。

**二、它把"不确定"当成正式结果。**
每一条培养要求都带状态，是已满足还是待人工确认，页面直接写出来。信息不足时说"还不知道"，不说"没问题"。

**三、它只建议，不替学生决定。**
换班建议生成后课表不动，学生本人确认后才生效。课程等价这类问题一律交回学校认定。

## 七、架构条（一行式，用于页面底部）

```text
成绩单 → 培养要求评估 → 补修需求 → 本学期真实教学班 → 冲突检测与替代建议
      → 学生确认 → 本学期课表 → 未来学期课程路径
```

技术性质一行注明：

> 规则驱动 + 结构化数据 + 确定性规划；固定工具编排，AI 增强模块待接入。

## 八、Demo 真实事实（六条，供宣传页"现场演示"板块）

1. 演示覆盖从上传成绩单到未来学期路径的完整链路；
2. 本学期规划精确到**真实教学班**；
3. 教学班数据范围为**南校园 + 深圳校区**；
4. 换班建议必须由用户**明确确认**后才生效；
5. 未来学期只做**课程级**规划，不出现教师、时间、教室；
6. 演示过程**不联网抓取**学校系统，使用本地已验收数据。

---

## 九、人工确认 / 可信设计（三条）

- **认定留给人**：课程等价、学分差额、学院政策、条款歧义，系统不下正式结论，只列依据；
- **执行留给人**：不自动选课、不自动换班；手工填写的课表必须本人确认，改动后确认自动作废；
- **风险透明**：数据范围、待确认事项、未执行的偏好，全部如实展示，不隐藏、不改写。

## 十一、当前限制（四条，建议保留在宣传页底部小字）

1. 教学班数据范围为**南校园 + 深圳校区**，不是全校、不是完整学期数据；
