## 1. 项目一句话（one-liner）

**学航·转衔：面向转专业学生的学业路径重构原型（固定工具编排，AI 增强待接入）——把「缺什么（培养方案差异与补修判定）→ 现实里有什么（教学班供给）→ 怎么排进去（受限确定性检查与候选评估）」串成一条可复核的链路，并明确标出哪些算得出来、哪些必须由人确认。**

## 4. 项目简介（200–300 字，书面语）

学航·转衔面向转专业学生，解决旧专业已修课程、新专业培养要求与当前课表之间的衔接问题。系统按有出处的结构化输入与规则识别历史补修范围，把课程等价、学分差额与政策口径中的不确定项保留为待人工确认；再通过确定性时间检查与受限的组合可行性、替代教学班候选评估，输出建议方案、变更记录与未决事项。当前已实现文件读取、课程匹配、固定工具编排、本地规划接口与演示页面；偏好来自结构化表单，没有自然语言解析；大模型与检索尚未接入。比赛演示的教学班输入是明确标识的 Synthetic 演示快照，正式 Real E2E 证据等级为 LEVEL 0。系统不替代学校做课程认定，不执行选课或注册，也不保证任意输入都存在可行方案。

## 5. 三个创新点

### 创新点 1 · 把「课程认定的不确定性」放进产品主线，而不是当成异常处理

- **主张**：系统不假装能替学校判定课程等价，而是把「已满足 / 可能等价 / 待人工确认 / 已确认需补修」做成契约里的**一等状态**，让不确定本身可见、可流转、可人工回流。
- **证据来源**：`schemas/makeup_task.schema.json` 的四种状态 —— `required`（已确认需补修）、`possibly_equivalent`（可能等价，待人工确认）、`manual_confirmation`（待人工确认）、`satisfied`（已满足）；以及 `docs/interfaces/curriculum.md` 对人工确认边界的约定。

### 创新点 2 · 把「实际执行的代码」与「经证明的输入来源」拆成两个独立轴，并逐处标注

- **主张**：本项目不把「真实」笼统地当成一个标签，而是把「实际执行的代码」与「经证明的输入来源」作为两个相互独立的轴，在架构图、页面与文档里分别标注，⛔ 不允许一个 "Real" 字样同时充当两者。
- **证据来源**：`docs/architecture/COMPETITION_ARCHITECTURE.md` §2 图例（蓝色实线 = 实际执行代码；灰 / 米黄 / 紫虚线 = 输入来源），以及 `README.md` §5 的两轴定义与 §5.3 的模式对照表。

### 创新点 3 · 受限的确定性检查 + fail-closed 的诚实拒绝

- **主张**：规划侧只做确定性时间检查、受限组合可行性检查与替代教学班候选评估，保留已有班、只提出新增 / 候选建议；链路不完整时明确拒绝并且**不回退**到演示数据顶替结果。
- **证据来源**：`docs/interfaces/planner.md` 的 `PlannerProvider.plan(*, makeup_tasks, offerings, current_schedule, preference)` 四参数契约；`schemas/plan_result.schema.json` 的 `unresolved[].type`（`schedule_unknown` / `selection_required` / `missing_data` / `manual_confirmation`）；`docs/data/CASE_A_RUNTIME_WIRING.md` 的 5 个环境变量与 `503 real_pipeline_not_configured`。

## 6. 三个实用价值点（现在就能做到什么）

### 6.1 面向转专业学生

**现在就能做到**：输入目标学期与转专业上下文，看到一条按课程逐条标注状态的清单（`satisfied` 已满足 / `possibly_equivalent` 可能等价（待人工确认）/ `manual_confirmation` 待人工确认 / `required` 已确认需补修），一份按课程分组的教学班供给清单，以及一份把「排课信息未知」「需要明确选择」等事项单独列出的未决清单。⛔ 不写「帮学生少走弯路」这类未验证效果。

### 6.2 面向辅导员

**现在就能做到**：一眼看到哪些结论是确定性判定、依据是什么（每条 `MakeupTask` 带 `reason` 与 `source_evidence`），哪些必须交回学校认定；`changes`（变更记录）逐条写明「原教学班 → 调整为 + 调整原因」。⛔ 不写「降低辅导员工作量 N%」这类未实测指标。

### 6.3 面向教务 / 学院

**现在就能做到**：看到系统明确声明的责任边界 —— 不做正式课程认定、不执行选课与注册、数据来源逐项披露（`data_source` 标记 + 页面来源标签）、链路未装配时明确返回 `503 real_pipeline_not_configured` 而不是用演示数据顶替。⛔ 不写「已获某校采纳 / 背书」。

## 7. 三个技术点

### 7.1 固定工具编排与 Provider 契约

`PlanningOrchestrator` 是**固定顺序**的工具编排层，只做三件事：取 `MakeupTask[]`、取该学期 `CourseOffering[]`、把两者连同 `current_schedule` 与 `Preference` 交给 Planner 并**原样**返回同一个 `PlanResult`。它不判断缺什么课、不判等价、不检测冲突、不选班、不改写结果，也**不调用任何模型**。
跨模块只依赖公共契约：`schemas/*.schema.json` 与 `docs/interfaces/*.md`。三个 Provider 分别是 `CurriculumProvider.get_makeup_tasks()` → `MakeupTask[]`、`CourseDataProvider.get_course_offerings(semester)` → `CourseOffering[]`、`PlannerProvider.plan(...)` → `PlanResult`。

### 7.2 受限确定性检查与候选评估

Planner 的逐字权威口径：

> 已实现确定性时间检查、受限组合可行性检查及替代教学班候选评估。当前 Planner 保留已有班，仅在受限条件下提出新增/候选建议，并把无法确定的事项保留到 `unresolved` / 人工确认。

安全约束：冲突三态 `CONFLICT > UNKNOWN > CLEAR`；教学班 `meetings = []` 只表示「当前来源快照没有能形成公共 `Meeting` 的可用排课信息」，⛔ 不等于没有冲突、也⛔ 不等于没有上课时间；总体不变量 **UNKNOWN ≠ INFEASIBLE**。
⛔ 这不是全局优化器，不做 CP-SAT / ILP 求解，不自动选课 / 换班，不保证偏好全部执行。

### 7.3 fail-closed 与 provenance 分层

- **fail-closed（明确拒绝、不回退）**：真实链路任一前置条件未就绪 ⇒ `POST /api/v1/plan` 返回 `503 real_pipeline_not_configured`，**不回退**到 Mock、不用演示数据顶替真实结果、不返回任何 `PlanResult`；运行时装配**逐请求重新校验**。
- **provenance（来源证据）分层**：`data_source` 字段是**契约 / 来源声明**，⛔ **不是**来源证明；形状正确的 Synthetic 输入经 adapter 后同样可能带 `real` 枚举值。只有绑定具体 artifact 的**批准 provenance** 才能支撑「真实学校输入」的表述。
- **证据等级**：正式 Real E2E = **LEVEL 0**；已具备的是 **LEVEL 1（synthetic wiring capability，合成产物跑通装配）**；`ready` 只表示运行时输入通过 Store + Curriculum 的最终复验，⛔ **不等于 LEVEL 2**。LEVEL 2 还要求已批准的真实 Course Data provenance / handoff、与之精确对应的已验收整学期证据、已批准的真实 Curriculum provenance，且**不得有 Synthetic 替代**。

## 8. 局限（如实列出）

1. **教学班数据是 Synthetic 演示快照**：比赛版本的教学班输入为明确标识的合成演示快照，两种模式下都是人工 / 程序生成，⛔ 不是实时教务数据。
2. **LLM / RAG / GraphRAG 未接入**：无模型调用、无检索管线；页面标题中的 "AI Agent" 指产品方向与固定编排架构，⛔ 不代表本版本运行了模型推理、检索或生成式解释。
3. **无自然语言偏好解析**：`Preference`（偏好约束）来自**结构化表单**（学分上限、避免跨校区、回避时段、意向课程），⛔ 没有自然语言理解。
4. **北校园开课查询为外部系统阻塞，已挂起**：学校教务系统北校园开课查询存在稳定的深分页异常；整学期验收要求五个校区齐备，因此在该外部问题解决前**真实整学期验收尚不可产出**。当前版本⛔ 不探测、不绕过该阻塞，也⛔ 不声称该部分可用。
5. **Real E2E 的 LEVEL 2 / LEVEL 3 未完成**：本轮**没有**真实教务登录、没有真实全量 artifact；正式证据等级仍是 LEVEL 0，已具备的是 LEVEL 1（synthetic）的 wiring capability。
6. **`data_source=real` 只是来源声明，不是证明**：该字段是契约标记，⛔ 不能由它、也不能由 HTTP 200、端点名或 case 名称推断输入来自学校；此问题仍有待架构裁决。
7. **⛔ 不执行选课 / 注册**：系统输出的是**建议方案**与未决事项清单，不代表学校已完成任何审批或选课。
8. **`ready` ≠ LEVEL2**：`ready` 只证明运行时输入通过了 Store + Curriculum 的最终复验（可装配、可读取、逐请求重校验），⛔ 不证明真实学校来源。
9. **模式 1 的 `changes` / `risks` 是人工构造的演示样例**：`GET /api/v1/mock/demo` 回放**不运行** Curriculum / Planner；计算模式下当前 Provider 主要输出 `unresolved`，`risks` 可能为空。
10. **其它已记录缺口**：先修关系的真实来源尚无证据（现有真实培养方案样本中未发现明确的先修字段）；`Meeting` 不表达排课段级教师关联；不承诺任意输入都存在可行方案。

## 9. 下一步路线图

> 说明：以下为**方向与待办**，⛔ 不构成对未排期能力的承诺；未完成项不会被表述为已完成。

### 近期

- 统一对外材料口径：所有材料使用同一 canonical 定位，并把「模式 1 为回放 / 模式 2 执行实际代码」「教学班 Synthetic」「Curriculum 来源须逐项核验」写成条件化表述。
- 演示与提交材料落地：按实际可跑模式完成计时彩排、脱敏截图、slides 与录制视频；核对官方赛规（时长、格式、是否要求运行中的 AI 模型）与 portal 字段。
- 文档口径修正：`ready` 与 LEVEL 2 的关系、`data_source` 的声明性质、`risks` 在计算模式可能为空。

### 中期

- **解除外部阻塞后再推进**：北校园开课查询深分页异常若被解决，按既有两步验收链路补齐五校区，产出**真实整学期 Course Data acceptance**。
- **补齐真实 provenance**：真实 Course Data 的 provenance / handoff 与真实 Curriculum provenance 逐项留证，并按 `docs/e2e/REAL_E2E_EVIDENCE_PROTOCOL.md` 的清单推进 LEVEL 2 证据闭环（⛔ 不得以 Synthetic 替代）。
- **架构裁决**：`data_source` 标记的语义边界（声明 vs 证明）落到契约层。

### 长期（方向，未排期）

- **模型增强**：在确定性判定不被模型替代的前提下，探索由模型辅助理解输入、检索有出处的证据与生成解释；LLM / RAG / GraphRAG 目前**不在执行路径上**。
- **口径扩展**：容量、通勤、先修、偏好执行口径等非时间规则的人工确认流程细化。
- **适配其他专业 / 学校**：模块与契约提供适配边界，但每校培养方案、认定规则、身份映射与数据授权需重新核验（⛔ 不称"开箱即用"，目前没有第二所学校的部署证据）。
