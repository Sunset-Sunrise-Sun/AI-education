## 项目标题

**学航·转衔：面向转专业学生的 AI 学业路径重构 Agent**

## 副标题备选（选一条）

1. 把转专业之后的一堆零散课程问题，重构成一条可执行、可解释、可确认的学业路径
2. 转专业之后，学生需要的不只是一张新课表，而是一条重新接起来的路径
3. 先回答"我还缺什么"，再回答"这学期怎么排"

---

## 一、问题

转专业之后，学生面对的不是"选哪门课"这么简单。他要连续回答七个问题：

1. 我已经修过什么？
2. 目标专业还缺什么？
3. 哪些课程需要补修？
4. 本学期真实有哪些教学班可以上？
5. 当前课表冲不冲突？
6. 哪些问题必须人工确认？
7. 未来几个学期怎样把培养方案重新接起来？

这七件事现在散落在四个地方：成绩单在教务系统里，培养方案是一份文档，教学班在开课查询页面，课表在另一个页面。

学生只能靠截图、手抄和记忆把它们拼起来。拼错的代价是真实的：补错课、排冲突、多读一年。

**更棘手的是：大部分问题没有一个确定答案，而学生无法区分"已经确定"和"还不确定"。**

---

## 二、用户

| 用户 | 他最想要什么 |
|---|---|
| **转专业学生（主要用户）** | 一份看得懂、能对照检查、明确标出风险和待确认项的补修路径草案 |
| 辅导员 / 教务老师 | 一眼看清判定依据、风险点和需要人工介入的位置，不用每次重翻条款 |
| 学院负责人 / 评委 | 数据来源、责任主体、系统边界是否清楚、可复核 |

---

## 三、解决方案

把七个问题收成一条链路：

```text
成绩单  →  培养方案要求逐条评估  →  补修需求
        →  本学期真实教学班      →  课表冲突与替代教学班
        →  学生本人确认          →  本学期可执行课表
        →  未来学期课程级路径
```

解决方案有三个不妥协的设计：

1. **只给能证明的结论。** 每一条培养要求都带状态和依据，"待人工确认"就写"待人工确认"。
2. **只建议，不替学生决定。** 换班建议生成后课表不动，学生点了才生效。
3. **信息不足时说实话。** 数据缺失时的结论是"还不知道"，不是"没问题"。

## 四、产品流程（四步）

| 步骤 | 学生做什么 | 系统做什么 |
|---|---|---|
| **第一步：上传成绩单** | 上传本人成绩单 | 识别已修课程，覆盖几个学期、共多少门 |
| **第二步：填写当前课表** | 搜索课程加入，或手工录入并勾选确认 | 以"学期 + 课程号 + 教学班号"作为唯一身份，排课信息缺失时标为"待核验" |
| **第三步：设置偏好，生成方案** | 填学分上限、是否跨校区、不方便的时间段、意向课程 | 输出学业方案总览、历史培养要求评估、本学期推荐课表、本学期专业选修建议、待确认调整、未来学期路径、选修学分进度 |
| **第四步：确认调整** | 在"需要你处理"里点"采用调整"或"暂时保留当前班" | 只有点"采用调整"才重新计算并返回新课表，其余课程保持不变 |

页面的信息顺序也做了取舍（这是真实人工验收后改的）：

```text
学业方案总览  →  本学期推荐课表  →  本学期专业选修建议
→  需要你处理  →  未来学期修读路径  →  详细依据（折叠）
```

最初把所有待确认事项平铺出来，会出现 11 张卡片、一门课 60 个候选堆在一页的情况。
现在换班建议按**课程**分组，一门课一张卡片，默认只显示 3 个候选，其余折叠；
待确认事项归入唯一的"需要你处理"中心，并去重、翻译成中文，原始代码收进"查看技术详情"。

## 五、技术

四层结构：

```text
前端（Vue 3 单页应用）
      ↓
后端（FastAPI）
      ↓
编排层：固定工具编排（只编排，不做业务算法，不调用模型）
      ├── 培养方案模块：差异分析与补修判定
      ├── 课程数据模块：本学期教学班供给
      └── 规划模块：受限确定性检查与替代教学班候选
      ↓
建议课表 / 变更记录 / 风险 / 待人工确认事项
```

**技术性质（必须如实表述）**：

- 规则驱动 + 结构化数据 + 确定性规划；
- **固定工具编排**，不是自主决策 Agent，也不是多 Agent 协商；
- 规划是**受限的确定性检查与候选评估**，不是全局最优；
- **AI 增强模块待进一步接入**：当前没有大模型推理、没有检索增强、没有知识图谱推理，偏好来自结构化表单。

一句话：**规则负责确定性判断，算法负责约束检查，人负责正式规则、权限边界和最终确认。**

## 六、数据

### 当前实际使用的数据范围

| 数据 | 当前状态 |
|---|---|
| 目标专业培养方案 | Case A 已确认的培养方案（网络空间安全方向） |
| 已修课程 | 本人成绩单（识别已修课程，但**不参与**已满足判定） |
| 本学期教学班 | **南校园 + 深圳校区**的真实教学班数据，共 **4069 条**（case-scoped） |
| 当前课表 | 学生本人填写并确认 |

### 必须一起说清楚的四件事

1. 教学班数据是**两个校区**的范围，**不是**全校，**不是**完整学期数据（页面标注"全校完整学期数据：否"）；
2. 未来学期**没有**教学班数据，也**不预测**，只用培养方案事实；
3. **当前 accepted Course Data 快照未保留教师字段，因此教师信息暂未同步**，系统不编造教师；
4. 上传的成绩单**不参与**"已修完 / 已满足"判定，已满足事实来自已确认的培养方案事实。

一句话版：**"真实教学班数据，范围是南校园 + 深圳校区，共 4069 条。"**

### 两个 23 必须分开

| 说法 | 含义 |
|---|---|
| **23 项** | 历史培养要求评估条数（12 项已确认满足 + 11 项待人工确认） |
| **23 学分** | 目标专业选修组的最低毕业要求（是学分，不是课程门数） |

## 八、价值

### 对学生的价值

- 把"我到底还差什么"从一次性的焦虑，变成一个可以逐条核对、可以保存、可以拿给老师看的清单；
- 把"这学期怎么排"从手动试排，变成一次带冲突解释的建议；
- 把"哪些要问老师"提前列出来，不用等到选课出问题才发现。

### 对学校的价值

- 转专业学生的学业咨询有了共同的事实基础，老师和学生看的是同一份清单；
- 认定类结论仍然由学校下，系统只负责把依据和风险摆清楚，**不越权**；
- 过程可复核，责任边界清晰。

### 对项目的价值

- 结构不绑定某一所学校：换培养方案、换校区、换认定规则，改动集中在数据适配层；
- 每一轮评估结果和确认记录都会沉淀下来，越用越准。

> ⚠️ 本版本**没有**准确率、成功率、使用人数或用户研究方面的实测数据，⛔ 不要在这些位置上填数字。

## 九、局限与下一步

### 局限（必须保留）

1. 课程等价认定、学分差额、学院特殊政策一律**待人工确认**，系统不下正式结论；
2. 教学班数据是**南校园 + 深圳校区**的 scoped 数据（4069 条），不是全校、不是完整学期；
3. 未来学期只做**课程级**规划，不预测教师、时间、教学班、容量；
4. **不执行**选课与注册，输出是建议方案；
5. 大模型、检索增强、知识图谱、自然语言偏好解析**尚未接入**；
6. 不保证所有偏好都被执行，未被执行的部分会如实出现在待确认事项里；
7. 先修关系的真实来源目前没有证据；
8. **当前 accepted Course Data 快照未保留教师字段，因此教师信息暂未同步**（不是原始接口没有教师数据）；
9. 成绩单**不参与**已满足判定，已满足事实来自已确认的培养方案事实；
10. 未来学期学分硬上限为 35，当前学期上限为 30，两者不同。

### 下一步

- 完成产品化界面定稿与最终截图；
- 落地并复核未来学期学分硬上限调整；
- 恢复教师字段需要重新访问实时接口（属于下一轮数据工作）；
- 扩大课程数据覆盖范围（这是数据工程问题，不是算法问题）；
- 接入 AI 增强模块：理解输入、检索证据、生成解释；
- 在真实院系场景中做小范围人工验收。
