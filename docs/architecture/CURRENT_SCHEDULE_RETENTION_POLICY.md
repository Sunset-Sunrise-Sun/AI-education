# 当前课表保留策略（Current Schedule Retention Policy）— 设计说明

> 状态：**设计提案（DESIGN ONLY）**。本文件**不**引入任何实现，**不**修改公共 Schema，
> 也**不**改变当前运行时行为。
> 适用模块：Planner / Path Planner（`backend/app/planner/`、`backend/app/path_planner/`）。

## 1. 为什么需要这个策略

转专业学生的当前课表里，不同课程的"可动程度"其实不一样：

```text
A. 固定课程 / 固定教学班   —— 例如必修且只有一个班、或学生已锁定
B. 课程固定、教学班可调     —— 例如同一门课有多个平行班，可换班避让冲突
C. 用户可灵活取舍的选修     —— 例如专业选修池里"修够学分即可"的课程
```

`RestrictedPlanner` 目前**没有**区分这三者：它对每个当前教学班一律只做"报告 + 建议"，
⛔ 不自动换班（这是正确的保守行为，本策略不改变它）。

但要真正做 Path Repair，就必须知道"这门课能不能动"。缺了这个信息，
Planner 只能一律保守 —— 于是"能修的冲突"和"不能动的课"无法区分。

## 2. 最小模型提案

建议引入一个**显式的、按门课声明**的策略取值：

```text
retention_policy ∈ {
    "fixed",              # A：课程不可动、教学班也不可动
    "class_adjustable",   # B：课程必须保留，教学班可换（需用户显式选择）
    "flexible_elective",  # C：可整体放弃 / 替换成同学分的其它选修
}
```

关键设计约束：

- **必须显式声明**：⛔ 绝不从课程名、课程类型、学分或"看起来像选修"来**推断**；
  无法确认时按 `fixed` 处理（fail closed）。
- **默认值 = `fixed`**：即"什么都不说"时，行为与今天**完全一致**。
- **不表达优先级**：本字段只回答"能不能动"，⛔ 不回答"先修哪门"（那是学业优先级，
  由 Curriculum / 人工负责）。

## 3. 它应该放在哪里

两条候选路径：

| 方案 | 位置 | 优点 | 代价 |
| --- | --- | --- | --- |
| **① Case A / Integration 编排元数据**（本轮推荐） | `app/path_planner/` 内部输入，或 `/api/v1/case-a-demo/*` 的加法字段 | ⛔ 不动公共契约；可先验证语义；随时可撤 | 只有该编排路径能用 |
| ② 未来公共契约字段 | `schemas/*.schema.json` + `docs/interfaces/*` | 所有调用方统一 | **破坏性契约变更**，需 Architecture Lead 单独批准 |

⛔ **本轮不得选择方案 ②**。公共 Schema / `Preference` / `PlanResult` 的字段变更
必须走独立的《接口变更请求》并获人工批准。

## 4. 遗留请求的默认行为

```text
请求里没有 retention_policy
    ⇒ 每个当前教学班按 "fixed" 处理
    ⇒ 与当前实现**逐字一致**的行为：
       冲突 → 报告 + 生成建议（若存在 CLEAR 候选）
       应用 → 只有用户显式选择后才发生
```

⛔ 不得出现"缺字段就当成可动"的宽松默认 —— 那会静默扩大自动改动范围。

## 5. Fail-closed 语义（提案）

| 情形 | 期望 |
| --- | --- |
| 取值不在白名单内 | 拒绝该请求（明确的配置/输入错误），⛔ 不猜测 |
| 声明 `class_adjustable` 但该课程无 CLEAR 候选 | 如实报告"无可确认候选"，⛔ 不编造 |
| 声明 `flexible_elective` 但缺少等价替代的证据 | 仍按**保留**处理并报 unresolved，⛔ 不自动丢弃课程 |
| 同一课程出现互相矛盾的策略声明 | 拒绝（不静默取其一） |
| `fixed` 课程被提交为换班目标 | 拒绝（⛔ 不得绕过 `from_class_id` 的"不可动"声明） |

## 6. 与 Phase 1 实现的关系

Phase 1（本分支 `feature/path-planner-core`）**刻意不实现本策略**，只：

- 保留当前行为：`current_schedule` 中的课程**一律保留**，直到用户显式确认换班为止；
- 已提供"生成建议 / 显式应用 / 重新校验"三段式接口
  （见 `app/path_planner/repair_proposals.py`），因此将来接入本策略时
  **不需要**改动换班原语的语义。

## 7. 待 Architecture Lead 决定的事项

1. 采用方案 ① 还是 ②（本轮建议 ①）；
2. 白名单取值最终命名与粒度（是否需要"整门课可放弃"与"教班可换"的中间态）；
3. 是否需要 `Preference` 承载（注意：那会改变公共契约语义，需单独批准）；
4. 当 `flexible_elective` 生效时，是否需要额外的"学分不得减少"约束（⛔ 本文件不预设）。
