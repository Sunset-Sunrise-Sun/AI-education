# 真实数据获取规划（Phase 2B-0A）

> **状态：规划模板。** 本文件目前只建立框架与待填写条目，**尚未获取任何真实数据**。
>
> **本轮范围（Phase 2B-0A）**：只做"数据获取规划"。**不抓取数据、不写爬虫、不登录教务系统、
> 不获取任何真实个人数据。** 实际的技术侦察与样本采集属于后续阶段（Phase 2B-0B 及以后），
> 须由负责人另行下发任务书。
>
> 数据安全分层与禁止事项见第 5 节，**五类数据全部适用**，不得因为某类数据"看起来不敏感"而绕过。

---

## 1. 本文件的作用与边界

**作用**：在写任何真实对接代码之前，先把"我们需要什么数据、从哪来、能不能拿、拿到后怎么存"
说清楚，避免出现三种危险做法：

1. 先写代码，再回头找数据；
2. 用猜测代替学校正式规则；
3. 把真实个人数据顺手提交进仓库。

**边界**：

- 本文件**只规划**，不代表已经获得授权，也不代表数据源已经确认；
- 所有"预计来源"在没有人工核实之前，都只是**待确认的假设**；
- 本文件**不定义任何公共字段**；真实数据与现有 Schema 的落差记录在
  `REAL_TO_SCHEMA_GAP_REPORT.md`，且**只记录、不改 Schema**；
- 本文件**不得**写入未经确认的具体链接，实际链接统一登记在 `DATA_SOURCE_REGISTRY.md`。

| 使用模块 | Curriculum（主）、Agent/Frontend（向用户展示判定依据）、QA/Demo（案例合法性） |
| 预计来源 | 学校教务处 / 相关学院的**公开规章制度与通知栏目**：学籍管理规定、转专业实施办法、课程认定 / 学分互认办法等。**具体文件与链接待人工确认后登记**，本文件不写链接 |
| 是否公开 | 待确认。通常此类办法为公开文件，但**必须逐份核实**（部分可能仅校内可见） |
| 是否需要登录 | 待确认（公开栏目一般不需要；校内 OA / 内网栏目需要） |
| 需要的最小字段 | 文件标题、发布机构、发布日期、适用学年、适用专业 / 对象、与补修或认定相关的**条款原文位置（章节号）**、文件生效状态 |

| 允许的采集方式 | 公开文件的人工下载与引用；记录完整出处（机构 + 标题 + 日期 + 章节） |
| 禁止的采集方式 | 绕过登录获取校内文件；批量爬取政策栏目；**把对条文的猜测或推断写成"学校正式政策"** |
| 是否包含个人信息 | 否 |
| 是否允许进入 Git | 待确认：**文件本身可否入库需先确认转载 / 版权限制**。建议入库"出处 + 要点摘录"，原件按限制决定 |
| 脱敏要求 | 不含个人信息，无需脱敏。但摘录时不得夹带内部人员姓名、联系方式 |
| 当前状态 | **未获取（待人工确认可用文件清单）** |
| 下一步行动 | ① 负责人确认可引用的正式文件清单；② 登记到 `DATA_SOURCE_REGISTRY.md`；③ 摘录与补修 / 认定直接相关的条款；④ 无法确认的条目一律标记"待人工确认"，不得下确定性结论 |

## 5. 数据安全分层与禁止事项

### 5.1 三层数据（Raw → Sanitized Sample → Mock）

```text
┌─────────────────────────────────────────────────────────────┐
│ Raw（原始数据）                                              │
│  · 可能含姓名、学号、成绩、Cookie / Session 痕迹              │
│  · 默认【不进入 Git】，只保存在负责人控制的受控位置            │
│  · 【不得直接交给其他成员】                                   │
└───────────────────────────┬─────────────────────────────────┘
                            │ 人工脱敏：去除直接身份标识
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ Sanitized Sample（脱敏样本）                                 │
│  · 已去除姓名、学号、身份证、联系方式                         │
│  · 经负责人确认后才可交付给 Curriculum / Planner 成员         │
│  · 是否允许入库 Git 需【逐项确认】                            │
└───────────────────────────┬─────────────────────────────────┘
                            │ 人工构造（不使用任何真实数据）
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ Mock（演示数据）                                             │
│  · 位于 /mock_data/，全部人工虚构                             │
│  · 【继续保持人工虚构，不允许用真实数据覆盖】                  │
│  · 必须继续明确标记为 Mock，不得冒充真实学校数据               │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 红线（对全部五类数据一律适用）

**禁止**：

1. 保存密码；
2. 保存 Cookie / Session / Token；
3. 绕过登录 / SSO；
4. 破解验证码；
5. 越权获取（枚举未授权数据、访问他人数据）；
6. 高频批量请求学校系统；
7. 提交可识别用户身份的成绩单或任何个人数据；
8. **将猜测写成学校正式政策**；
9. 把 Raw 个人数据直接交给其他成员。

任何任务如果要求上述行为，**立即停止并报告 BLOCKED**（见 `/docs/SECURITY.md` 第 6 节）。

### 5.3 与现有仓库规则的关系

- 本节的规则是 `/AGENTS.md` 第 7、8、11、18 节与 `/docs/SECURITY.md` 在"数据获取"场景下的具体化；
- 冲突时以 `/AGENTS.md` 为准；
- `/mock_data/` 的现状与约束见 `/mock_data/README.md`，本阶段**不修改该目录**。

## 6. 与公共 Schema 的关系

真实数据进入系统前，必须先确认现有公共 Schema 能否承载。
**无法映射时只记录潜在缺口，不修改公共 Schema**，分析框架见 `REAL_TO_SCHEMA_GAP_REPORT.md`。

一句话原则：

> 数据要迁就契约，不能契约迁就数据；确需改契约时走 `【接口变更请求】` 并由负责人决定。
