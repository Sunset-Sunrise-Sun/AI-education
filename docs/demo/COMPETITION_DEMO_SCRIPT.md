# 学航·转衔 · 比赛 Demo 演示脚本（3–5 分钟）

> **一句话定位**：「学航·转衔」是一个**面向转专业学生的学业路径重构原型（固定工具编排，AI 增强待接入）** —— 它把「转专业后要补什么、这些课什么时候开、怎么排得下、哪些必须由人拍板」讲成一条**可复核**的链路，而不是替学生下结论。

| 项 | 内容 |
| --- | --- |
| 演示形式 | 现场投屏，主讲人一边操作页面一边讲解 |
| 总时长 | **3–5 分钟**（推荐 4 分钟版，各场景建议时长见小标题） |
| 页面入口 | 前端 Vite 地址（默认 `http://127.0.0.1:5173`），后端 `http://127.0.0.1:8000` |
| 用例背景 | 中山大学场景，Case A：2025 级 遥感科学与技术 → 网络空间安全，目标学期 `2026-1` |
| 实现边界 | **固定工具编排原型**；**LLM / RAG / GraphRAG 尚未接入**（无模型推理、无检索管线、无自然语言偏好解析） |

## 0. 事实基线（开讲前先认清，脚本中不得越界）

1. **两个轴必须分开说**：①**实际执行的代码**（`CurriculumCaseProvider` / `StoreBackedCourseDataProvider` / `RestrictedPlannerProvider` / API/runtime / 前端渲染确实执行）；②**输入来源**（是否具备批准 provenance 的真实学校数据）。⛔ 前者不证明后者；⛔ 一个"Real"字样不得同时充当两者。
2. **本轮的证据等级仍是 LEVEL 0**：没有真实教务登录、没有真实全量 artifact。⛔ 脚本中不得声称已达成 LEVEL1 / LEVEL2 / LEVEL3，也不得声称已完成 Real E2E；⛔ `ready` ≠ LEVEL2。
3. **北校园开课查询采集已作为外部系统阻塞挂起**（稳定的深分页异常）。本脚本不涉及继续探测，也不声称该部分可用。
4. **当前实现能力**：结构化读取、规则分析、固定 Provider 编排、受限确定性时间检查与替代候选评估已实现；**模型理解 / 检索 / 生成式解释为未来方向**（"未来可由模型辅助理解输入、检索证据与生成解释；当前版本由结构化输入、规则和固定编排执行"）。⛔ 不说"AI 正在理解 / 解析 / 解释本次演示"。
5. **系统不代替人做认定**：规则做确定性判断，受限检查做时间与候选评估，**人负责正式规则、权限边界和最终确认**。
6. **系统不执行教务操作**：不注册、不选课、不提交任何教务指令；输出永远是**建议方案**与**未决事项清单**。
7. **模式 1 不执行上游业务计算**：页面回放预置的 Mock 样例，`changes` / `risks` 是人工构造的演示例子，⛔ 不是本次现场求解结果。

## 2. 模式选择（先确认模式，再开讲）

### 2.1 两种演示模式

| 模式 | 名称 | 运行前提 | 数据来源 | 适用场合 |
| --- | --- | --- | --- | --- |
| **模式 1（默认）** | **演示回放** | 干净检出即可运行；**不设置任何真实链路环境变量** | 基础数据（MakeupTask / CourseOffering / Preference）与 PlanResult **全部来自** `GET /api/v1/mock/demo`（读取仓库内已提交、并通过 `/schemas/*.schema.json` 校验的 `mock_data/*.json`）。⚠️ **不执行上游业务计算**：Curriculum / Planner 代码不参与，`changes` / `risks` 是人工构造的样例 | **默认使用**；可复现、风险最低 |
| **模式 2** | **计算模式** | 操作者本机持有**显式本地 Case A manifest**（`APP_CASE_A_CURRICULUM_CASE_PATH`，来源须由批准 provenance 证明）+ 一份**已验收的整学期 Course Data SQLite 库** | `POST /api/v1/plan` **执行实际代码**：CurriculumCaseProvider → Curriculum Diff → MakeupTask → RestrictedPlanner → `PlanResult`（含 unresolved / 人工确认；`risks` 可能为空）；**页面基础展示区仍为 Mock 演示数据**；**教学班（CourseOffering）输入是明确标注的 Synthetic 演示快照** | 本机确实具备上述显式本地输入时 |

> ⚠️ **模式 2 的显式前置条件**：Case A manifest **不在 Git 仓库中**，属于操作者的受控本地输入；
> 其**真实学校来源**须由绑定该 artifact 字节的**批准 provenance** 另行证明（⛔ `data_source=real`、HTTP 200、端点名都不是证明）。
> ⛔ 绝不能用合成 case 冒充真实 Case A；⛔ 不具备该输入时就用模式 1。

### 2.2 两种模式的界面差异（必须讲清楚）

| 界面位置 | 模式 1（回放） | 模式 2（`POST /api/v1/plan` 成功后） |
| --- | --- | --- |
| 第 4 区「4. 规划结果与建议课表 (PlanResult)」来源标注 | `基础演示数据：Mock · 规划结果：Mock`（**回放预置结果**） | `基础演示数据：Mock · 规划结果：Real`，并注明本区块方案来自 `POST /api/v1/plan` 的**实际代码计算**、**其余区块仍为 Mock 演示数据**；⛔ 实际执行 ≠ 输入真实 |
| 第 1 区「1. 历史培养要求评估（MakeupTask）」 | Mock 演示数据 | **仍为 Mock 演示数据** |
| 第 2 区「2. 开课教学班供给 (CourseOffering)」 | Mock 演示数据 | **仍为演示快照**，并显示「教学班数据：演示快照（Synthetic）」 |
| 第 3 区「3. 学生个性化偏好 (Preference)」 | Mock 演示数据 | **仍为 Mock 演示数据**（偏好来自结构化表单，⛔ 无自然语言解析） |
| 「生成规划（Real Planning）」按钮 | 默认不可用（未开启 `VITE_PLAN_API_ENABLED`），这是**预期默认行为** | 可用（输入完整 + 课表来源门禁通过） |

**关键口径**：`POST /api/v1/plan` 返回的**只有 PlanResult**；页面**不会**把整页统一标成 Real，也⛔ 不会在失败时回退到 Mock 冒充真实结果。

### 2.3 启动方式（对应仓库实际命令）

```powershell
# 后端（工作目录 backend/）
$env:PYTHONUTF8="1"; python -m uvicorn app.main:app --reload --port 8000
#   健康检查：GET http://127.0.0.1:8000/health

# 前端（工作目录 frontend/）
npm install      # 首次
npm run dev      # Vite 开发服务，默认 http://127.0.0.1:5173
```

- **模式 1**：不设置任何真实链路环境变量；前端不设置 `VITE_PLAN_API_ENABLED`（默认关闭）。
- **模式 2**：后端需**恰好 5 个**显式环境变量 —— `APP_REAL_CASE_A_ENABLED=1`、`APP_CASE_A_CURRICULUM_CASE_PATH`、`APP_COURSE_DATA_SQLITE_PATH`、`APP_COURSE_DATA_SEMESTER`、`APP_COURSE_DATA_ACCEPTANCE_SHA256`；前端需 `VITE_PLAN_API_ENABLED=true`（可选 `VITE_PROXY_TARGET`，默认 `http://127.0.0.1:8000`）。
- **fail closed**：以上任一缺失 / 非法 ⇒ `POST /api/v1/plan` 返回 `503 real_pipeline_not_configured`，**绝不回退**到 Mock。⛔ 这不是系统故障，而是设计上的**诚实拒绝**。

## 3. 八个场景（统一结构：目标 / 主讲人说 / 操作 / 预期界面表现 / 评委看点 / 兜底话术）

### 场景 1 · 转专业背景｜建议 20 秒

| 项 | 内容 |
| --- | --- |
| ① 场景目标 | 说清「输入从哪里来」：这是一个真实的转专业情境，不是抽象功能演示 |
| ② 主讲人说 | 「我们从一个学生开始。他原来是遥感科学与技术，转专业进入网络空间安全，现在要规划的是 2026 学年第一学期。页面的第 0 区专门收集这类输入：目标学期、转专业上下文、当前课表和个人偏好。请注意一句：本区块只组织输入，不做冲突检测、也不生成补修任务。」 |
| ③ 操作 | 滚动到第 0 区「0. 用户输入（目标学期、转专业上下文、当前课表与偏好）」；指出子区块「① 学生信息（目标学期与转专业上下文）」中的目标学期 `2026-1`、原专业、目标专业、转入学期；再指出「② 已修课程文件（成绩单）」「③ 当前课表（current_schedule）」「④ 个性化偏好（Preference）」 |
| ④ 预期界面表现 | 顶部品牌头「学航·转衔」+ 数据来源标头显示后端 `X-Data-Source` 的实际取值；下方醒目的 Mock 警示条；四步流程引导条（培养方案对比 → 教学班供给获取 → 偏好约束注入 → 课表求解与调班 Path Repair）；第 0 区子区块标题与输入框按上述顺序排列 |
| ⑤ 评委看点 | 输入与结论**解耦**：输入区不产生任何业务结论；成绩单文件只保存文件名与文件对象（**不上传、不解析、不推断**），页面明确说明补修识别必须由后端 Curriculum 模块完成 |
| ⑥ 兜底话术 | 「如果这一区显示为空或字段没填上，不影响后面看结果——当前展示的是演示快照回放；具体输入以页面实际显示为准，我们不在这里现场编数据。」 |

### 场景 2 · 学业差异｜建议 25 秒

| 项 | 内容 |
| --- | --- |
| ① 场景目标 | 说明「差异」是怎么被组织的：目标培养方案要求 vs 已修记录，先看整体，再看逐条 |
| ② 主讲人说 | 「转专业真正的难点是差异：新培养方案要求哪些课、他原来修过什么、两者之间的缺口有多大。页面用两个地方表达这件事：上面是概览计数，下面是逐条评估。**具体数字以页面实际显示为准**，我不在这里口算。」 |
| ③ 操作 | 指向页面顶部概览状态卡片（「历史培养要求评估项」「教学班记录」「单学期学分上限」「规划结果状态」），再指向页面顶部的 **8 场景演示路线**第 1–3 项（转专业背景 / 学业差异 / 历史培养要求评估） |
| ④ 预期界面表现 | 概览状态卡片显示三类计数与规划结果状态标签；8 场景路线可点击跳转到对应区块；第 1 区的副标题写明「Curriculum 模块依据目标培养方案要求与学生已修记录逐条评估后的结果」 |
| ⑤ 评委看点 | 差异不是「猜」出来的：**Mode 2 由 Curriculum 模块实际计算**、**Mode 1 为回放预置结果**；无论哪种模式，前端只做展示、不重算、不汇总改写 |
| ⑥ 兜底话术 | 「页面上没有单独一块叫『学业差异』的图表——差异按设计就落在概览计数和第 1 区的逐条判定里。如果数字和我刚才说的不一致，**以页面实际显示为准**；这些是演示快照数据，不是真实教务数据。」 |

### 场景 3 · 历史培养要求评估（第 1 区 MakeupTask）｜建议 35 秒

| 项 | 内容 |
| --- | --- |
| ① 场景目标 | 展示系统**不做过度断言**：同一条课程要求，可以有完全不同的结论状态 |
| ② 主讲人说 | 「这一区是整套系统的判定核心。每一条课程要求都有一个状态，界面上实际会出现四种判定文案：『已满足』、『可能等价（待人工确认）』、『待人工确认』、『需要补修』。我特别想请评委注意：**『待人工确认』和『可能等价（待人工确认）』都不等于需要补修**——它们是两种不同的东西：一种是证据不足、要请人认定；一种是已经确认需要补修。讲解时我会用中性说法：已满足 / 待课程认定 / 已确认需补修，逐条状态以每行的判定列和认定说明为准。」 |
| ③ 操作 | 定位第 1 区「1. 历史培养要求评估（MakeupTask）」；从上往下逐条念判定列，并展开/指出每行的「认定说明」（reason），必要时指出 `source_evidence` 中的 `mock://` 前缀，说明这是演示数据 |
| ④ 预期界面表现 | 区块标题带 `Mock` 标记与条数徽标；每行显示课程号 / 课程名 / 学分 / 判定标签 / 认定说明 / 先修与截止学期等字段；标签文案来自前端标签映射（`已满足`、`可能等价（待人工确认）`、`待人工确认`、`需要补修`） |
| ⑤ 评委看点 | **人机边界**：系统只给出确定性的判定与依据，凡涉及课程等价、学分差额这类学校正式规则，一律留给人工确认，不由模型或前端拍板（当前也没有模型参与判定） |
| ⑥ 兜底话术 | 「如果我念的某一条状态和界面上的判定列不一致，**以界面为准**——我不覆盖系统的输出。当前用的是演示快照数据（`mock://` 来源，非真实培养方案）；即使某一条看起来像需要补修，也必须经人工认定才成立，我们不做任何替代认定的表述。」 |

### 场景 4 · 教学班供给 + 学生偏好（第 2、3 区）｜建议 40 秒

| 项 | 内容 |
| --- | --- |
| ① 场景目标 | 说明「课程缺口」如何落到**具体教学班与具体时间**上，并在此处**一次性、明确地**披露教学班数据的性质 |
| ② 主讲人说 | 先念**披露口径（逐字）**：「**教学班数据：演示快照（Synthetic）**。」随后念既定说明（逐字）：「由于学校教务系统北校园开课查询存在稳定的深分页异常，当前比赛版本的教学班演示使用经过明确标识的 Synthetic 快照。系统的培养方案解析、补修判定、约束规划、Path Repair、风险解释与前后端运行链路仍按正式架构执行。」紧接着补一句**来源分层**（逐字）：「这段说的是**代码按正式架构执行**；**输入来源需逐项核验**——教学班是 Synthetic 快照，页面基础展示区仍是演示数据。」然后继续往下讲，不重复致歉：「第 2 区就是教学班供给：按课程分组，每个教学班显示班号、授课教师、排课与时间地点、容量、数据源。第 3 区是学生偏好：学分上限、是否避免跨校区、回避时段、意向课程——偏好是**结构化输入**的约束条件，不是结论（本版本没有自然语言解析）。」 |
| ③ 操作 | 定位第 2 区「2. 开课教学班供给 (CourseOffering)」，指出顶部统计「覆盖课程 N 门 / 候选教学班 N 个」；若某行排课列显示中性标签，指出它就是「**当前数据中无排课信息**」；再定位第 3 区「3. 学生个性化偏好 (Preference)」，念出学分上限、避免跨校区、回避时段与意向课程 |
| ④ 预期界面表现 | 第 2 区带 `Mock` 标记与条数徽标，表格列依次为「教学班号 / 授课教师 / 排课与时间地点安排 / 容量情况 / 数据源」；容量列显示「剩余 / 总数」；数据源列显示该教学班的 `data_source` 取值；当 `meetings` 为空时，排课列显示中性标签「当前数据中无排课信息」；第 3 区显示 Preference 各字段 |
| ⑤ 评委看点 | ①**数据边界诚实**：教学班是 Synthetic 演示快照，页面显式标注；②**中性数据状态**：排课信息缺失时说「当前数据中无排课信息」，绝不推断成没课、也绝不下任何可行性结论；③偏好以**结构化输入**传递（⛔ 本版本无自然语言解析），⛔ 不保证全部偏好都被执行——须结合 `unresolved` 与人工确认 |
| ⑥ 兜底话术 | 「如果界面上暂时看不到 Synthetic 标注，我先当场口头更正：本轮教学班演示用的是**经过明确标识的 Synthetic 快照**，不是真实教务数据；然后**跳过教学班区块的细节讲解**，只按既定口径说明一次，不反复解释、不现场补数据。若某个教学班的时间列是空的，那正是『当前数据中无排课信息』这一中性状态，不是我们漏了数据。」 |

> ⚠️ 一个真实行为提醒：Real 提交有**课表来源门禁**——只放行「当前课表为空」或「每一项都明确为真实教学班（`data_source = real`）」两种情况。演示时若把演示快照教学班勾进当前课表，提交会被门禁**直接阻止且不发请求**。模式 2 演示前请把当前课表留空。

### 场景 5 · 风险与未决（第 4 区 risks / unresolved）｜建议 30 秒

| 项 | 内容 |
| --- | --- |
| ① 场景目标 | 展示「风险透明」：方案不是一句『没问题』，而是把不确定性逐条摆出来 |
| ② 主讲人说 | 「现在进入第 4 区的风险与未决事项。⚠️ 先说明来源：**模式 1 这里展示的是人工构造的演示样例，不是本次现场算出的风险等级**；在计算模式中，以实际 Planner 的输出为准——当前 Provider 主要输出的是未决事项（`unresolved`），`risks` 可能为空。页面不会告诉我们『放心选』，它把不确定的东西逐条列出来：比如某个教学班剩余容量很少；比如某门课是否需要补修取决于人工对学分差额的判定。**具体条目与等级以页面实际显示为准**。如果某个教学班在当前数据中没有排课信息，系统会把它作为『排课信息未知』如实报告，而不会据此下可行性结论。」 |
| ③ 操作 | 定位第 4 区中的「方案风险提示 (risks)」小节（为空时改看「待解决与待确认事项 (unresolved)」）；逐条念出风险等级标签（高/中/低）与原因文本；注意 KPI 里的「风险提示」「未决事项」计数 |
| ④ 预期界面表现 | 第 4 区内有 KPI 条（建议课表教学班 / 方案调整 / 风险提示 / 未决事项）与方案状态徽标（如「部分可确认」及对应说明）；`risks` 为空时显示「本次 PlanResult 未返回风险项。」；排课信息缺失的情形会以「排课信息未知」类未决事项出现在 `unresolved` 中 |
| ⑤ 评委看点 | ①**来源分层**：Mode 1 的 `risks` 是演示样例，计算模式以实际 Planner 输出为准，⛔ 不说"系统实时算出风险等级"；②排课信息缺失时坚持中性表述「当前数据中无排课信息」，不作出「时间上可行」这类结论；③容量、人工判定等不确定性被显式暴露，而不是被方案结论掩盖 |
| ⑥ 兜底话术 | 「如果风险区是空的，那只表示**这份结果里没有风险条目**——计算模式下当前 Provider 主要输出未决事项，所以风险条可能为空。这不代表方案没问题：任何方案的可执行性都要在真实教学班与真实认定结果下重新验证。我不会替它下『风险可控』的结论。」 |

### 场景 6 · 受限修复与变更记录（第 4 区 changes）｜建议 30 秒

| 项 | 内容 |
| --- | --- |
| ① 场景目标 | 展示变更记录的**字段语义与限制**：不是"系统自动调班"，而是受限条件下的候选/新增记录 |
| ② 主讲人说 | 「Mode 1 这里展示的是**人工构造的变更样例，并不是本次现场 Planner 求解**。在计算模式中，系统会执行受限的确定性检查和替代候选评估；当前 Planner **保留已有班并要求人做选择**，`changes` 可能只是 `required` 任务唯一 CLEAR 候选的**新增记录**。所以：**当前 Planner 不保证按所有偏好自动换班，也不是全局优化器。**每一条变更仍写清三件事：原来在哪个教学班、调整到哪个教学班、为什么记录这条变更——**具体原因文本以页面实际显示为准**。」 |
| ③ 操作 | 定位第 4 区中的「教学班调整对比与成因 (changes)」小节；逐条对照「原教学班 → 调整为 + 调整原因」三段；配合 KPI「方案调整」计数 |

| ② 主讲人说 | 「这里是方案主体：建议课表教学班。请注意用词——这是**建议方案**，页面上每个班级的标签是『建议纳入』，**不是**已经选上的课、更**不是**已经注册。方案还有一个总体状态和一个求解目标说明：比如当前状态是『部分可确认』，意思是仍存在排课信息未知、需要人工选择或尚未完成认证的事项。」 |

### 场景 8 · 人工确认模型（第 4 区 unresolved）｜建议 25 秒

| 项 | 内容 |
| --- | --- |
| ① 场景目标 | 收尾落在系统最核心的设计原则：**系统不代替人做认定** |
| ② 主讲人说 | 「最后一块，也是我们认为最重要的一块：待解决与待确认事项。每一条都带着它的**原始类型**展示，比如 `manual_confirmation`（待人工确认）、`missing_data`（缺少数据）、`schedule_unknown`（排课信息未知）、`selection_required`（需要明确选择）。这些不是缺陷列表，而是**边界声明**：课程等价关系、学分差额是否补修、信息不足时的判断——系统全部交回给人。所以这套系统的定位不是替学生决定，而是让人做决定时手里有完整的证据和风险清单。」 |
| ③ 操作 | 定位第 4 区中的「待解决与待确认事项 (unresolved)」小节；逐条念出类型标签与说明文本；指出 KPI「未决事项」计数与页面上的说明「系统不会自行做假定或强行下结论」 |

| ⑤ 评委看点 | ①**类型不被归一**：不同原因分别展示，不会把所有未决事项笼统写成「待人工确认」；②**人机权责清晰**：规则判定、受限检查给候选、人做最终确认（⛔ 本版本没有模型解释环节）；③诚实：不把未决事项藏进方案结论里 |
| ⑥ 兜底话术 | 「如果这一区没有条目，那是当前演示快照里没有未决事项，**不等于**真实场景下不存在需要人工认定的问题——真实数据接入后，这类事项仍会按类型如实列出。我不会把没显示出来的东西说成已经确认。」 |

## 5. 常见提问与回答

**Q1：这些数据是真的吗？**

> 「分两部分说。页面**基础展示数据**（历史培养要求评估、开课教学班、学生偏好）来自后端 Mock 演示通道，页面顶部有醒目标识、每个区块带 `Mock` 标记，后端响应头是 `X-Data-Source: mock`。**规划结果**区块只有在成功调用 `POST /api/v1/plan` 之后才会标成 `Real`，含义是**这段方案由实际代码计算**（Actual API computation）——即便那时，其余区块仍标注为 Mock 演示数据。这里要区分两件事：**实际代码执行**不等于**输入数据已获得真实学校来源认证**。两类内容都不代表真实教务系统的正式指令。」

**Q2：为什么教学班是 Synthetic？**

> 逐字回答：「由于学校教务系统北校园开课查询存在稳定的深分页异常，当前比赛版本的教学班演示使用经过明确标识的 Synthetic 快照。系统的培养方案解析、补修判定、约束规划、Path Repair、风险解释与前后端运行链路仍按正式架构执行。」（补充一句即可）「所以『教学班是演示快照』和『这套代码按正式架构执行』这两件事同时成立；但**输入来源仍需逐项核验**——Curriculum 是否属于真实学校输入，要看该次 artifact 的批准证据，而不是看字段或标签。」

**Q3：系统会不会替学生选课？**

> 「不会。系统不注册、不选课、不执行任何教务操作。它的输出是**建议方案**——页面上每个班级的标签是『建议纳入』——同时把需要人工认定的课程等价、学分差额等问题原样列在『待解决与待确认事项』里。最终确认权在学校与学生。」

**Q4：为什么后端会返回 503？**

> 「这是 fail closed 设计，不是故障。计算模式需要**恰好 5 个**显式环境变量（`APP_REAL_CASE_A_ENABLED=1`、`APP_CASE_A_CURRICULUM_CASE_PATH`、`APP_COURSE_DATA_SQLITE_PATH`、`APP_COURSE_DATA_SEMESTER`、`APP_COURSE_DATA_ACCEPTANCE_SHA256`），并且需要操作者本机持有**可加载的显式本地 Case A manifest** 和**已验收的整学期 Course Data 库**。缺任一项就返回 `503 real_pipeline_not_configured`，而且**绝不回退**到 Mock 去冒充真实结果。Case A manifest 属于操作者受控的本地输入、不在仓库里，且其真实学校来源须由该次批准 provenance 另行证明，这是显式前置条件。」

**Q5：你们这个阶段的完成度到底到哪？**

> 「本轮的正式 Real E2E 证据等级是 **LEVEL 0**：没有真实教务登录、没有真实全量 artifact。我们展示的是完整的前后端运行链路与诚实的 provenance 机制——Mock 与计算模式严格分离、未装配时明确拒绝、风险与人工确认事项如实暴露。要特别说明两点：一是 **`ready` 只表示运行时输入通过了 Store + Curriculum 的最终复验，不等于 LEVEL 2**，LEVEL 2 还要求完整的真实 Course Data provenance / handoff 与真实 Curriculum provenance，当前教学班供给是 Synthetic，所以 `level2_eligible` 如实为 false；二是**当前未集成 LLM / RAG / GraphRAG**，是固定工具编排原型。北校园开课查询的采集还卡在外部系统的深分页异常上，我们没有把它算进已完成部分。」
